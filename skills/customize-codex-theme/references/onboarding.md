# 首次检查与引导

除非用户明确要求其他语言，默认使用简体中文。先运行只读 `doctor`，再按结果选择一种输出；不要把成功与 `NOT_READY` 混写。

## 环境就绪

按以下顺序报告真实字段，不能省略 Node.js，也不能把非空状态说成“干净的初始状态”：

```text
环境检查已通过：
- 操作系统：<Windows/macOS>
- Codex 版本：<version>
- Node.js：<version>（来源：<Codex 内置/系统 PATH>；签名发布者：<publisher>；Node.js 20+、Authenticode 与内置 WebSocket 校验通过）
- 主题状态：<未发现/逐项报告 selected、next、loaded、previous>
- 调试端点：<未发现/已验证>
- 主题启动器：<未发现/逐项报告路径、所有权判定、将执行的创建/保留/迁移/拒绝动作>
- 本次操作：仅完成只读检查，未修改任何文件，也没有重启 Codex
```

只有主题状态、端点和启动器均为空时，才说明“当前处于干净的初始状态”。已有主题或任一非空状态时逐项如实报告，不得宣称干净，并提供继续定制、切换、修复或恢复选项。

随后说明五种入口：

1. **发送参考图片**：分析构图、配色、对比度及宽屏/分栏/窄屏裁切，再用“想要的感受、第一视觉标志、工作时插画显示强度”三项创意简报生成三种真正不同的预览方向。
2. **描述主题风格**：普通用户只需回答想要的感受、最先注意到的角色/场景/符号/纹理/材质、以及工作时插画要沉浸/留在空白/靠边/仅保留配色；代理负责转换为构图拓扑、阅读保护和响应式契约。
3. **让我推荐方案**：信息不足时只问 2–3 个关键偏好，再给三套推荐方向；分别说明配色、字体、界面材质、背景和可读性。不得让用户选择 schema、坐标所有者或运行命令。
4. **体验六套内置主题**：只有用户选择内置主题或第 4 种入口之后，才读取目录并展示六套简要预览卡；不自动应用，用户选中后再详细预览。
5. **检测主题质量**：用户只需说明主题名称、发送主题目录/截图，或直接说“检测当前主题”。代理自动执行只读环境、创意简报编译、单坐标所有权、关键阅读保护、主题注册信任、版本兼容、目录、像素合成对比度与覆盖率检查，并核对设计主张、主次焦点、安静阅读区、材质一致性、语义色感知距离及插画裁切/噪声风险。结果必须用普通语言按影响排序，给出“最强之处、最大风险、最值得做的下一步”和证据边界；不得输出一个伪精确的综合审美分数，也不得要求普通用户自己运行命令。检测本身不授权修改、切换、热更新或重启。

需要生成图片预览时，按实际能力选择图片路径：官方内置 `image_gen` 可用且未选择自定义中转时使用内置能力；API Key/中转或内置能力不可用时，读取 [image-generation.md](image-generation.md)，先用主题 SKILL 自带的 Image2 包装器做无网络探测，再通过 `gpt-image-2` 生成并完整校验真实 PNG。不得把 HTML、SVG 或文字说明冒充为已生成的图片预览。

公开包内置六套可再分发主题。用户本地还可安装私有系列与变体；Windows 可视化选择器的数量、名称和“系列 → 变体”分组必须始终来自验证后的 manifest，不得把固定的六套内置浏览集误报成用户机器上的全部已安装主题。

进入准备阶段前必须说明：主题只能通过独立的 **Codex Themes** 启动入口加载；**Codex Original** 启动入口始终打开未注入的原版 Codex，用于回退。Windows 的 **Codex Themes** 会显示可视化选择器，只列出通过目录校验的主题，按系列组织变体并显示经过本地资源校验的预览图，分别标明“下次启动”和“最近验证加载”；确认具体变体后才会受控重启已捕获并二次验证的官方 Codex 进程、更新下次启动主题并继续启动。选择系列节点、取消或关闭都不会修改状态，也不会关闭 Codex。询问用户是否要创建这两个主题自有入口，不得静默创建或覆盖现有快捷方式。

发现旧版受管 **Codex Themes** 时，先报告完整字段和拟执行的迁移动作并取得用户对创建/升级入口的同意。只有目标、参数、工作目录、描述和所有者全部匹配已知旧签名时才能事务式升级；未知或部分匹配的同名快捷方式必须拒绝处理。迁移不得重写 **Codex Original**，且必须验证其文件内容保持不变。

结尾请用户回复序号，或直接发送图片/风格描述。

## Node.js 未就绪

若没有可信的 Node.js 20+ 运行时，或缺少内置 WebSocket，输出 `NOT_READY`，报告已发现的操作系统、Codex、Node.js 失败原因及其余可确认状态，并明确本次未修改、未安装、未重启。

- 不得静默或自动安装，也不得先安装再征求同意。
- Windows：`doctor` 报告“没有可信运行时”不等于系统没有 Node.js。先只读解析 Codex 内置候选和系统 `PATH` 中现有 `node.exe` 的绝对路径；适配器必须在执行版本或 WebSocket 探针之前验证 Authenticode 状态与允许的官方发布者。不得用环境变量重定向验证运行时，也不得持久化变量或静默修改 `PATH`。确实缺失时，只有获得用户当前轮明确授权，才从官方来源安装 Node.js LTS。安装前说明来源、版本、安装范围、`PATH` 与管理员权限影响；安装后重跑签名、版本和 WebSocket 校验。
- macOS：主题适配器只信任 Codex 内置且签名匹配的 Node.js。缺失或签名/兼容性失败时，优先修复、更新或重新安装官方 Codex；不得用 Homebrew 或系统 Node 绕过签名校验。
- 用户拒绝安装或修复时保持 `NOT_READY`，不继续准备或应用主题。
